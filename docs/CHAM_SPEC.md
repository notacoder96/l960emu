# CHAM.sys (960L reverb-card NT4 driver) — behavioural spec

Sources: `CHAM.sys` (image base 0x10000, 29 920 bytes, identical on DriveD/DriveE) and the callers in `ChamAPI.dll`.
Annotated per-function disassembly: `/tmp/claude-0/cham/funcs.asm` (generated by `fn.py` / `rd.py` in the same folder).
Unless marked ASSUMPTION, everything below is read directly from the code.

## 0. Objects

DriverEntry 0x104fe: `IoCreateDevice("\Device\CHAM", ext 0x12C, FILE_DEVICE 0x22)`, symlink `\DosDevices\CHAM`.
MajorFunction: CREATE 0x10780, CLOSE 0x10840 (completes OK), DEVICE_CONTROL 0x10860, Unload 0x10b0e. No StartIo.

## 1. PCI discovery, BAR, HI32 register map

* 0x10f50: for bus 0.., slot 0..31: `HalGetBusData(PCIConfiguration, bus, slot, buf, 0x100)`; match VendorID 0x1057 && DeviceID 0x1801 (Motorola DSP56301). Records {bus, slot, cfg[0x2C] (SubsystemVendorID)}; stops at 2 cards or when HalGetBusData returns 0 (end of bus).
* 0x10c49 per card: HalAssignSlotResources → first memory range = BAR0 → HalTranslateBusAddress → MmMapIoSpace (non-cached). Interrupt: HalGetInterruptVector + IoConnectInterrupt(ISR 0x11457, context = card, level-sensitive, shared).
* 0x10e4a: HalGetAdapter. 0x10ef0: allocate the 4 KB common buffer.

HI32 host-side registers used (32-bit READ/WRITE_REGISTER_ULONG at BAR0+off). Names per DSP56301 UM; the offsets/bit usage are confirmed by the code:

| BAR0 off | name | driver use | helper |
|---|---|---|---|
| 0x10 | HCTR | write 0x0A00 before every code download (HTF=10b bits 8-9, HRF=01b bits 11-12: 24-bit data in 32-bit dwords, right-aligned on both directions — ASSUMPTION about the exact format names; the driver always writes 24-bit values in the low bits and reads 24-bit values zero-extended) | 0x11c70 W_HCTR |
| 0x14 | HSTR | ISR: bit 6 = HINT (card is interrupting); bits 3..5 = HF3..HF5 = message class | 0x11cf0 R_HSTR |
| 0x18 | HCVR | write host-command vectors; bit0 = HC, bits1..7 = HV (vector addr = HV*2), bit15 = HNMI; polled until bit0 clears after download vectors | 0x11c90 W_HCVR, 0x11cd0 R_HCVR |
| 0x1C | HTXR (write) / HRXS (read) | data FIFO host→DSP / DSP→host | 0x11cb0 W_HTXR, 0x11d10 R_HRXS, 0x11d30 W_HTXR_dwords(card, u32*, n), 0x11d80 W_HTXR_bytes(card, u8*, n: one byte per write) |

The driver never polls HSTR TRDY/HTRQ before writing HTXR, nor HRRQ before reading HRXS: the emulated FIFO must accept back-to-back writes (thousands of words for a download) and must already hold the message words when the ISR reads them.

## 3. Open (IRP_MJ_CREATE, 0x10780) — per card, in order
1. card+0 = card+4 = 0, card+8/+0xC = BAR VA/len.
2. 0x10ef0: allocate common buffer if needed.
3. 0x11ee0: zero the 4 KB common buffer; 0x11fe0(card, -, virt, phys):
   * load ChamID.pci (3304 bytes = 826 dwords: {count=0x338, addr=0, words…});
   * HCTR=0xA00; HCVR=0x8073; spin while HCVR&1; DelayMs(5); write all 826 dwords to HTXR; DelayMs(5);
   * HCVR=0x79; HTXR=phys&0xFFFF; HTXR=phys>>16;
   * poll **common[0] != 0** every 1 ms, up to 3000 ms → else fail 0xC0000001 (card+0x50 = 0, CREATE fails → CreateFile fails).
   * on success: type = common[1]>>6 & 3, dbver = common[2]>>4 & 3, IDR = common[3]; valid = 1; subvendor = card+0x70.
   * zero the common buffer again.
   So the ChamID program must DMA (PCI master write) ≥4 nonzero-word-0 dwords to the host address it was given. Words are 32-bit little-endian dwords holding 24-bit values.
4. 0x12630: queue pointers.
Any failure completes CREATE with that status.

## 4. Common buffer layout (one 4 KB page per card, physical addresses go to the DSP)
```
0x000 Host cmd queue  : +0x00..0x3F current command (DSP reads this) ; +0x40 rd ; +0x44 wr ; +0x48 + 64*i ring[8]
0x248 Host response   : +0 mdlSlotLo, +4 mdlSlotHi, +8 count (dwords), +0xC.. data (24-bit, one per dword)
0x288 TMIX queue      : same shape as host queue
0x4D0 Periodic status : 48 dwords (DSP writes; dword0 overwritten by the driver with 0/2)
0x590 Z80#0 queue     : same shape
0x7D8 Z80#1 queue     : same shape
0xA20 Z80#0 response  : +0 mdlLo, +4 mdlHi, +8 count (BYTES), +0xC.. 3 bytes per dword, MSB first (bits 23..16, 15..8, 7..0)
0xA60 Z80#1 response  : same
```
Queue protocol (identical for host/TMIX/Z80 queues, 8 entries, indices mod 8, both maintained by the host):
* post: if ((wr+1)&7)==rd → ERRVAL 0x10003 (queue full). Else ring[wr] = cmd; if the queue was empty (wr==rd) also copy cmd to Q+0 and ring the queue's vector; wr=(wr+1)&7.
* completion (DPC): rd=(rd+1)&7; if not empty, copy ring[rd] to Q+0 and ring the vector again.
So the DSP only needs to read Q+0..0x3F when its vector fires, execute, optionally DMA a response, and raise an HF=3 message (§6). ASSUMPTION: the DSP does not use rd/wr.

IOCTL 0x58 (InitializeQueues, handler 0x126e0): in = {u32 card ≤ 2}. card+0=0; zero rd/wr of the 4 queues; HCVR=0x79; then 16 HTXR halfwords, lo then hi, of the physical addresses in this order: host queue (+0x14), host response (+0x1C), TMIX queue (+0x24), status area (+0x2C), Z80#0 queue (+0x38), Z80#1 queue (+0x3C), Z80#0 response (+0x48), Z80#1 response (+0x4C). Returns immediately.

## 5. IOCTLs (all METHOD_BUFFERED, device 0xA410; dispatch 0x10860, index = (code-0xA410EC40), byte table 0x10a3c / jump table 0x10a10)
IRP completion: Information = handler result, Status = 0 or 0xC0000001. ChamAPI treats a nonzero bytes-returned value as an ERRVAL error code. Overlapped handles are used by ChamAPI but every IRP completes synchronously.

|---|---|---|---|---|

### 64-byte command block (u32 fields, built by ChamAPI)
```
+0x00 opcode            +0x04 card index         +0x08 unit: 1=host, 2/3=Z80 #0/#1, 4=TMIX
+0x0C event slot lo16   +0x10 event slot hi16    (normaliser: if +0x0C holds a 32-bit value it is split)
+0x14 data count        +0x18.. data[0..9]
```
The DSP echoes the event slot (and MDL slot via the response area) back.

Host opcodes (SendHostCommand, ChamAPI 0x10002430: data = PAKI array, count dwords):
| op | ChamAPI | data |
|---|---|---|
| 1 | EnableWordclockMixer | {bool} (count 1, no event, no wait) |
| 2 | Poke56301 | {space, addr, value} |
| 3 | PokeIO | {addr, byte} |
| 4 | SetIOmaster | – |
| 5 | Peek56301 | {space, addr, mdlLo, mdlHi} — driver splits data[2]/[3]; response 1 word |
| 6 | PeekIO | {addr, mdlLo, mdlHi} — driver splits data[1]/[2] |
| 7 / 0xB | ResetZ80 #0 / #1 | – |
| 8 / 0xC | UnResetZ80 #0 / #1 | – |
| 9 / 0xD | ResetLexichip (arg 0 / ≠0) | – |
| 0xA / 0xE | UnResetLexichip (arg 0 / ≠0) | – |
| 0xF | PokeBit | {space, addr, bit, value} |

Z80 opcodes (SendZ80Command 0x10002900; data packed bytes are LITTLE-endian in 24 bits: byte i at bits 8*(i%3) of data[1 + i/3]):
| op | ChamAPI | data |
|---|---|---|
| 1 | LoadBulk(bank, addr, n, bytes) | {n \| bankcode<<16, addr, 8 words of packed bytes} count 10 (≤24 bytes) |
| 2 | FetchBulkDump(bank, addr, n) | {n \| bankcode<<16, addr, mdlLo, mdlHi} count 4; driver splits data[2]/[3]; response in Z80 response area (bytes MSB-first) |
| 6 | RunSingleFunction(bank, addr) | {bankcode, addr} count 2 (RunDoubleFunction = both Z80s) |
| 7/8/9/0xA | SendLexichipCommand for bank 0/1/2/3 | {n ≤ 0x1C, packed bytes…} count 10 |
bankcode: Z80_RAM_BANK 1→1, 2→2, 3→3, else 0 (FetchBulk/LoadBulk put it in bits 16..17). RunZ80Kernel = LoadBulk of four u16 entry points (0 → 0x0206) to Z80 address 0x26.
Opcode names of the Z80-side Lexichip commands (byte 0 of the Lexichip payload) are in EnumsOrig.dll 0x100038d8: 0 START_LEXICHIP … 35 SET_CHORUS_VOICE_COUNT.

TMIX opcodes (unit 4): 1 Register {tmixId+1, reg, value&0xFF} count 3; 2 Map {tmixId+1, mapAddr, 8 words packed BIG-endian (byte i at bits 16-8*(i%3))} count 10; 3 DPRAM {tmixId+1, addr&0xFFFF, s32 value} count 3.

ChamAPI waits after posting: GrabCard (mutex), IOCTL 0x60 with the card's completion event (this+0x132C), post, WaitForThunderEvent(event, timeout, default 6000 ms) → "WaitForCard … Timed out" on expiry. So every command whose slot ≠ 0 must eventually produce a completion message carrying that slot.

## 6. ISR (0x11457) and DPC (0x11560)
ISR(card):
1. ignore unless the card is in devExt's list and HSTR bit 6 (HINT) is set.
2. f = (HSTR >> 3) & 7 (HF3..HF5). HCVR = 0x7B.
3. f == 1 or 2: w = HRXS; card+0 = (w == 0xA98765); return TRUE.
   f == 3: w0 = HRXS, w1 = HRXS, w2 = HRXS; KeInsertQueueDpc(card DPC, w0, (w2<<16)|w1); return TRUE.
   f == 0 or ≥4: return FALSE.
DPC(card, w0, slot): acquire devExt+0x0C lock; HCVR = 0x87; dispatch on w0 & 0xFF:
| w0&0xFF | handler | effect |
|---|---|---|
| 1 | 0x12fd0 host | if (w0 & 0xFF0000)==0x10000: copy readback — mdl = resp[0] \| resp[1]<<16, n = resp[2], copy n dwords (masked 0xFFFFFF) from resp+0xC into the locked user buffer, unlock MDL. Then SignalEvent(slot) if slot≠0; advance host queue (next → Q+0, HCVR 0x7D) |
| 2 / 3 | 0x13210 Z80 #0/#1 | if (w0 & 0xFF0000)==0x10000: Z80 response (0x13280): mdl from resp[0..1], n = resp[2] BYTES, unpack ceil(n/3) words MSB-first into the user buffer. SignalEvent(slot); advance; next → HCVR 0x83/0x85 |
| 4 | 0x13510 TMIX | SignalEvent(slot); advance; next → HCVR 0x7F |
| 5 | 0x13630 status | status[0] = (w0 & 0xFF00) ? 2 : 0; card+4 = 0 (no event) |
Finally completes DeviceObject->CurrentIrp if any (never set — no StartIo). ASSUMPTION: the DSP writes the status area by DMA before sending type 5.

Message word summary (DSP → host via HRXS, HF3..5 = 3): w0 = class (bits 0-7) | error (bits 8-15, status only) | hasData (bits 16-23 == 1); w1 = slot low16; w2 = slot high16.

## 7. Timing / registry
* PreCommandDelay before posting IOCTL 0x48/0x50/0x4C: DelayHost/DelayZ80/DelayTMIX µs (registry, default 0 in the 960L hive), stall vs sleep per EmployDelayKeStallCPU (=1 on the 960L).
* Download paths: spin on HCVR.HC, then 5 ms sleep before streaming words; ChamID: 5 ms after streaming, then up to 3 s poll of common[0].
* ChamAPI (not the driver): Sleep(100) between the Z80-kernel download and InitializeQueues; Z80 download is skipped if card type ≠ 0.

## 8. Implications for the emulator (helper bridge)
Three IOCTLs pass user-space pointers/handles that the remote bridge cannot touch; the hook DLL must handle them locally:
* 0x60: keep slot → HANDLE in the hook; on a completion message with that slot, SetEvent(HANDLE).
* 0x64: keep MDL slot → (VA, len) in the hook; the bridge returns readback bytes with the completion, the hook writes them to VA.
* 0x5C: buf[1] is a user pointer; the hook copies the 0xC0-byte status snapshot returned by the bridge to it.
Everything else (download words, queue contents, vectors, HF messages) can be modelled in the bridge on top of an emulated HI32 + host-memory (common buffer) that the 56301's PCI master DMA reads/writes.
